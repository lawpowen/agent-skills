# UI 设计规范与技能导航

作为跨项目页面和组件设计任务的共同入口，先查看用户要求、项目指令、现有页面、设计系统和技术栈，再应用本文件中的用户偏好并按需读取专项技能。用户明确要求与项目指令、已确认的设计方向和可访问性要求优先；不因使用导航而扩大改动范围或替换技术栈。若项目已有自己的 UI 标准入口，按项目指令先读该入口，本技能作为补充，避免循环调用或重复执行；项目局部版本与本全局版本各自维护。

## 默认调用流程

遵循项目指定的入口后，应用我们的规范，再按下面的顺序选择专项技能；设计或审查任务本身不授权实现、发布或修改项目文件。

`ui-design-standards → ui-ux-pro-max（按需） → 当前任务需要的专项技能或补充参考`

1. **先应用我们的规范。** 查看现有界面、设计系统和代码，落实本文件的用户偏好，尤其是减少不必要的次级标签和描述，让布局表达关系。
2. **再按需读取 `ui-ux-pro-max`。** 当需要配色、字体、布局、响应式、无障碍、交互或技术栈的具体建议时使用，并按其要求选择最小查询。沿用现有方案即可完成的简单文案或局部样式改动，不为走流程额外生成设计系统。
3. **涉及弹窗等反馈交互时，读取 `ui-feedback-patterns`。** 包括 Tooltip、Toast、Alert、Modal、Popconfirm、Drawer、Bottom Sheet、Action Sheet、Snackbar、AlertDialog、Tour、Lightbox、字段错误、确认、局部编辑和未保存输入保护；在决定组件和交互行为之前读取。若同时需要通用设计建议，先由 `ui-ux-pro-max` 提供建议，再由本专项技能细化组件选择、关闭、焦点、确认与撤销行为。
4. **涉及聊天与桌面工作台交互时，读取 `ui-chat-desktop-interactions`。** 聚焦 IME 发送、消息滚动、流式阅读、分栏拖动及文件名展示；若同时有弹窗或确认，再组合 `ui-feedback-patterns`，不要把所有桌面页面都导向聊天专项。
5. **需要视觉质感或微动效细化时，读取 [视觉与动效补充参考](references/visual-motion.md)。** 这是按需参考，不是新技能或强制风格；边框、暗色字重、同心圆角、流式文字、等宽数字和动画参数的核实集中在此。

核心包包含 `ui-design-standards`、`ui-ux-pro-max`、`ui-feedback-patterns`、`ui-chat-desktop-interactions` 和 `frontend-design`。其他技能按当前会话可用清单和项目局部指令选择，缓存中存在文件不等于可调用；缺少可选技能时用现有工具继续，不自动安装依赖或替换项目技术栈。

其他 UI 技能按下方导航进入相应分支，不能跳过我们的规范，也不需要一次性加载所有技能。用户明确指定的方案与项目约束优先，工具的强制前置技能仍需遵守。

## 我们的设计规范

### 让布局解释界面，减少多余说明

用户原文：**avoid unnecessary secondary labels and descriptions. Let the layout do the explaining**

默认避免不必要的次级标签和描述，让分组、层级、间距、对齐、位置与组件形态传达关系。每一段辅助文字都应提供用户完成任务所需的新信息；删去重复标题、复述按钮或仅解释显而易见布局的文案。

- **先整理结构，再补说明。** 内容关系不清时，优先调整分组、标题层级和操作位置，不靠堆叠副标题、说明段落或 Tooltip 弥补布局问题。
- **不要给每个区块套一层文案。** 不默认添加装饰性 eyebrow、小标题、卡片副标题、功能介绍和重复状态标签；只有它们实际帮助识别内容、状态或下一步操作时才保留。
- **保留必要信息。** 字段名称、数值单位、日期范围、费用、限制、错误原因、恢复方式和危险操作后果不能为追求简洁而丢失。标题能区分区块时保留标题，辅助描述能解决真实歧义时保留描述。
- **简洁不能损害可访问性。** 不把 placeholder 当作字段标签，不移除控件的可访问名称，不用图标、颜色、空间位置或只能悬停查看的提示承载必需含义。视觉分组应有相应的语义结构。

这条规范追求清晰而克制的界面，不要求所有产品采用同一种极简风格，也不禁止有用的说明文字。它作用于产品界面，不应被误用为删除用户请求的交付说明。

### 取舍示例

| 场景 | 默认处理 | 保留条件 |
|---|---|---|
| “项目”标题下写“在这里管理您的所有项目” | 删除重复描述，让列表和“新建项目”按钮表达用途 | 有实际的权限、范围或操作限制需要说明 |
| 导航已选“设置”，页面又堆叠“SETTINGS / 设置 / 管理您的设置” | 保留一个适当的页面标题，按任务分组 | 返回路径或层级确实需要额外定位信息 |
| “收入”卡片中的金额没有币种和期间 | 保留或补足币种、统计期间 | 不把理解数据所必需的标签当成冗余 |
| 删除确认中解释不可恢复的后果 | 保留对象、后果和明确动作按钮 | 不能仅靠红色按钮或垃圾桶图标表达后果 |

## 按任务选择 UI 技能

从当前会话的可用技能清单定位相应 `SKILL.md`，读取后遵循其中适用的工作流。技能名称是导航索引，不是已经读取或执行的证明。只加载当前任务需要的技能；多个技能解决不同问题时可以组合，不必把整张表全部调用。

| 当前任务 | 读取的技能 | 分工与边界 |
|---|---|---|
| 需要新的视觉方向，且现有设计系统不足以确定取舍 | `frontend-design` | 作为默认流程后的可选分支，补充产品视觉方向、排版和布局；不因新建页面就跳过我们的规范或自动重做设计系统 |
| 页面或组件的 UX、响应式、无障碍、配色、字体或技术栈实现 | `ui-ux-pro-max` | 按其任务契约选择设计系统、单一领域或已检测技术栈的查询；已有设计系统优先复用 |
| 提示、确认、弹窗、抽屉、底部面板、动作选单、引导、媒体查看和字段错误 | `ui-feedback-patterns` | 覆盖原提示组件及 Bottom Sheet、Action Sheet、Snackbar、AlertDialog、Tour、Lightbox、Inline error；处理模态性、焦点、关闭、撤销与输入保护 |
| 聊天输入、流式消息列表、桌面可调分栏与文件名展示 | `ui-chat-desktop-interactions` | 处理输入法、跟随阅读状态、拖动恢复与识别信息；不替代通用页面设计或弹窗选型 |
| 现有页面的视觉质感、暗色排版、边框圆角与微动效 | [视觉与动效补充参考](references/visual-motion.md) | 按需结合 `ui-ux-pro-max`；区分已核实机制、工程建议与场景参数，不复制视频固定数值 |
| 检查已有 UI 的体验、响应式和无障碍 | 当前可用的审查技能，例如 `product-design:audit` 或 Web Design Guidelines | 根据真实界面、用户任务与改动范围检查；具体规范以适用的官方标准核实，未验证的部分明确标注 |
| React / Next.js 页面、组件或性能 | 当前可用的 React Best Practices | 仅在项目实际使用 React 时选择，结合版本、项目约定和具体问题；不将其规则套用于 Vue、Django 模板等 |
| 使用 shadcn/ui 的 React 项目 | 当前可用的 shadcn/ui 专项技能 | 先核对现有依赖、版本、组件和主题；不为调用技能引入组件库或改变技术栈 |
| 手机 App 界面、Sleek 项目或 Sleek 设计的代码实现 | `sleek-design-mobile-apps` | 按其移动端设计流程执行；保留本文件的界面文案规范，遵守认证、费用和外部数据访问边界 |
| Figma 设计转代码 | `figma:figma-design-to-code` | 先读取该技能，再调用设计上下文工具；涉及 SwiftUI 或动画时再加载对应技能 |
| 向 Figma 创建或修改页面、组件、设计系统 | 对应 `figma:*` 技能 | 按下方 Figma 导航选择；不能用本文件替代工具的强制前置技能 |
| 建站、修改或发布 Sites 网站 | `sites:sites` | 保持用户指定的建站工具与目标；仅查询 UI 规范不意味着创建或发布站点 |

### Figma 与辅助能力导航

| 需求 | 技能入口 | 何时补充 |
|---|---|---|
| 组装完整页面、弹窗、抽屉或多区块视图 | `figma:figma-generate-design` + `figma:figma-use` | 需要在 Figma 中写入或检查相应节点时 |
| 组件、变量、token、主题和组件库 | `figma:figma-generate-library` + `figma:figma-use` | 包括单个可复用 Figma 组件 |
| 新建 Figma 文件 | `figma:figma-create-new-file` | 每次调用新建文件工具前 |
| SwiftUI 与 Figma 双向转换；动效实现或写入 | `figma:figma-swiftui`；`figma:figma-implement-motion` / `figma:figma-use-motion` | 按方向及是否涉及 Figma 写入再组合基础技能 |
| 页面确实需要图片资产或交互可视化 | `imagegen`；`visualize:visualize` | 只有资产或可视化服务于用户任务时使用，不为装饰自动添加 |

未列出的专项任务（例如 Figma Code Connect、Code Layers）按当前技能清单中的对应描述选择。不在本文件复制各技能的完整说明，也不固定插件版本路径。某个技能不可用时，说明限制并使用现有能力完成允许的部分；本导航不授权安装工具、发送私密数据或发布内容。

## 执行与验收

### 新增规则的证据边界

用户的明确偏好可记录为我们的规范；外部视频只用于定位待核实问题，不能单独成为技术标准依据。新增技术规则先查 W3C、平台/浏览器或组件库官方资料，并在对应专项或参考中记录来源、核实日期与适用范围。证据只证明 API 能力时，不把某套 UX 策略说成标准要求；未证实为通用规则的尺寸、延时、比例、字重或弹簧参数标为可调方案，不设为默认“铁律”。

### 按本次改动验收

1. 先看现有界面、相关代码或设计资料，确定用户的主要任务、现有设计语言和本次改动边界；无需为了小改动重新设计整页。
2. 应用上述文案规范，并读取实际需要的技能。用户明确要求与项目约束优先；通用技能的风格建议不能覆盖本文件的用户偏好。
3. 实现后检查：删掉辅助文字后，用户是否仍能判断内容、操作、状态和后果；若不能，先改善结构，再补最少且具体的必要文字。
4. 按改动检查真实界面、窄屏、键盘与相关交互。条件不允许时明确未验证部分，不把文件检查说成视觉或行为验收，也不为纯静态文案机械添加测试。

本规范来自用户在本次对话中的明确偏好；后续新增 UI 偏好时，集中更新“我们的设计规范”，避免散落到每个专项技能中。导航只负责选用技能，不覆盖其工具前置条件、现有授权和访问限制。
